# Code Design Guidelines for LLM Assistants

## Core Philosophy

I value **working, minimal solutions** over comprehensive designs. My codebase is already structured well — extend it, don't reinvent it.

## Before Proposing New Abstractions

Ask yourself:
1. Can this be solved by adding a field to an existing struct?
2. Can this be solved by adding a method to an existing impl?
3. Can this be a simple conditional branch in existing code?

If yes to any → do that instead of creating new types.

## Constraints (Treat as Hard Rules)

- **No new lock types** unless I explicitly ask for them
- **No new wrapper structs** just for "cleaner separation" — I'll ask if I want that
- **No design docs with diagrams/tables** unless requested — give me code-first answers
- **No "future-proofing"** abstractions — solve today's problem only
- **Prefer `Option<T>` and simple enums** over struct hierarchies

## How I Think About Locking

- Fewer locks > more locks
- Coarser locks held briefly > fine-grained locks held longer
- If the current lock strategy works, keep it
- Don't introduce lock hierarchies to "prevent" problems I haven't encountered

## How to Respond to Design Questions

1. **Start with the minimal change** — show me the smallest diff that works
2. **Only then** mention alternatives if there are meaningful tradeoffs
3. **Don't create markdown design docs** unless I ask — prefer inline code comments
4. **When I say "don't worry about X"** — truly ignore X, don't design around it

## Red Flags in My Prompts (Push Back)

If I say things like:
- "probably should..." → Ask: "Is that necessary, or should we try without first?"
- "give me ideas" → Ask: "Want the simplest working approach, or exploring options?"
- "keep X ready for Y" → Ask: "Do you need Y now, or should we defer?"

## Code Style Preferences

- Functions over methods when the logic isn't tied to one struct's identity
- `impl` blocks for data-centric behavior, free functions for orchestration
- Early returns over deep nesting
- Explicit over clever
- `// TODO:` comments for known limitations rather than speculative abstractions

## Example: Good vs Over-Engineered

**Over-engineered** (what I don't want):
```rust
struct WalFileManager {
    active: Rc<RwLock<ActiveFile>>,
    registry: Rc<RwLock<FileRegistry>>,
    // ...
}
struct ActiveFile { /* ... */ }
struct FileRegistry { /* ... */ }
struct FileEntry { /* ... */ }
```

**Good** (what I want):
```rust
// Add to existing ShardMemCache:
current_log_id: u64,

// Add method:
pub fn rotate_to_next_log(&mut self, log_id: u64, meta_pos: u64, data_pos: u64, file_len: u64) {
    self.current_log_id = log_id;
    self.metablocks_position = meta_pos;
    // ...
}
```

## When Complexity IS Warranted

- I'll explicitly say "this needs a new abstraction because..."
- Performance data shows the simple approach doesn't scale
- The simple approach requires duplicating significant logic
```
